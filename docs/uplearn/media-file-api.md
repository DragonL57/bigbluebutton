# Media file API contracts

Contracts for phase 2 (upload and synchronized playback) and phase 3 (recording). Every name marked
proposed is new in this fork. Names without that mark exist in upstream `v4.0.x-release` at the commit
recorded in `README.md`.

## Terminology

The feature is one concept, an uploaded media file played to the room, and every identifier carries
the word `media`: `mediaFile` for the file, `mediaPlayer` for the playback session, `mediaUploadToken`
for the upload authorization, `mediaBaseUrl` for the serving prefix. Do not reuse `presentation`
identifiers, and do not call the same thing `audio` in one place and `media` in another; the same
file may be audio or video.

## Data model

The schema lives in `bbb-graphql-server/bbb_schema.sql` and is applied wholesale by
`bbb-graphql-server/deploy.sh`, which drops and recreates the `bbb_graphql` database. A new table
therefore arrives with a normal deploy; no separate migration file exists.

### v_mediaFile_uploadToken (proposed)

Mirrors `v_pres_presentation_uploadToken` (`bbb-graphql-server/bbb_schema.sql:1794`). The client polls
this view because it is the reliable path; the direct akka response can arrive before the client
subscribes.

```sql
CREATE OR REPLACE VIEW "v_mediaFile_uploadToken" AS
SELECT "meetingId", "mediaFileId", "uploadUserId", "uploadTemporaryId", "uploadToken"
FROM "mediaFile"
WHERE "uploadInProgress" IS FALSE AND "uploadCompleted" IS FALSE;
```

### v_mediaFile (proposed)

The presenter panel lists the files uploaded in this meeting.

```sql
CREATE OR REPLACE VIEW "v_mediaFile" AS
SELECT * FROM "mediaFile" WHERE "uploadCompleted" IS TRUE;
```

## GraphQL actions

Actions live in `bbb-graphql-actions/src/actions/` and are dispatched by name through
`bbb-graphql-actions/src/index.ts` and `src/imports/redisMessageFactory.ts`. Each file builds one
Redis message. The presentation and external video actions are the model
(`presentationRequestUploadToken.ts`, `externalVideoStart.ts`).

| Action (proposed) | Input | Guard | Emits |
|---|---|---|---|
| `mediaRequestUploadToken` | `filename: string`, `uploadTemporaryId: string` | `throwErrorIfNotPresenter`, both fields required, length at most 500 each as in `presentationRequestUploadToken.ts` | `MediaUploadTokenReqMsg` |
| `mediaStart` | `mediaFileId: string`, `displayMode: string` optional, default `full` | `throwErrorIfNotPresenter` | `StartMediaFilePubMsg` |
| `mediaUpdate` | `playing: boolean`, `positionSeconds: number`, `playbackRate: number`, `compact: boolean` | presenter only, plus the presenter check inside the handler | `UpdateMediaFilePubMsg` |
| `mediaStop` | none | `throwErrorIfNotPresenter` | `StopMediaFilePubMsg` |
| `mediaFileRemove` | `mediaFileId: string` | presenter only, checked twice: in the action and again in the handler | `RemoveMediaFilePubMsg` |

The size is server state, so every client shows the same arrangement, but it travels as a boolean:
`mediaFileUpdate` carries `compact` and the row keeps it in `playerCompact`. The design name for the
same idea was the string `displayMode`.

The names in these tables are the design names. The shipped ones are the five `mediaFile*` GraphQL
actions under `bbb-graphql-actions/src/actions/` and the messages in `MediaFileMsgs.scala`:
`MediaFileUploadTokenReqMsg`, `StartMediaPlayerPubMsg`, `UpdateMediaPlayerPubMsg`,
`StopMediaPlayerPubMsg`, `RemoveMediaFilePubMsg`. The size of the player is server state too, as the
boolean `compact` on `mediaFileUpdate`; whether a file has a compact form at all still comes from its
content type, and only audio does.

## Upload outcomes

The upload POST has more than one ending, and the row records which one it was.

bbb-web reports the outcome to akka-apps the way it reports a converted presentation. On success
the row gets the detected mime type, the size on disk and `uploadCompleted` true, and the meeting is
told a file is available. On refusal the row keeps an error key in `uploadErrorMsgKey` and is written
with `uploadInProgress` true, which is what takes it out of `v_mediaFile_uploadToken`; it never
reaches `v_mediaFile`, so a refused upload is invisible in the file list and the uploader's token
request ends in its timeout instead of waiting forever.

The keys are `media.upload.tooLarge`, `media.upload.unsupportedFormat`, `media.upload.notPlayable`,
`media.upload.emptyFile`, `media.upload.invalidName` and `media.upload.failed`.

`maxMediaFileUpload` is enforced in three places: the pre-check refuses a declared
`x-original-content-length` over the cap before nginx loads the body, the nginx location caps the
body at 205 MB, and the controller measures the bytes it stored and refuses and deletes them if they
are over the cap. The third is what covers a deployment where the property and the nginx value have
drifted apart.

`mediaPlayer.mediaFileId` is a composite foreign key with `meetingId`, so a player row can only
reference a file the meeting owns.

## HTTP endpoints

bbb-web serves both the upload and the file. The presentation controller is the model
(`bigbluebutton-web/grails-app/controllers/org/bigbluebutton/web/controllers/PresentationController.groovy`),
and the routing entries go into `bigbluebutton-web/grails-app/controllers/org/bigbluebutton/web/UrlMappings.groovy`.

| Route (proposed) | Action | Notes |
|---|---|---|
| `POST /bigbluebutton/media/$authzToken/upload` | `upload` | Multipart field `fileUpload`, plus `temporaryMediaId`; mirrors `/bigbluebutton/presentation/$authzToken/upload` |
| `GET /bigbluebutton/media/checkUpload` | `checkMediaBeforeUploading` | Internal `auth_request` target, mirrors `checkPresentationBeforeUploading` |
| `GET /bigbluebutton/media/checkAuthorization` | `checkMediaAuthorization` | Internal `auth_request` target, mirrors `checkPresentationAuthorization` |
| `GET /bigbluebutton/media/$meetingId/$mediaFileId/$filename` | `downloadMedia` | Only reached through nginx after `auth_request` succeeds |

Upload sequence, in the order the checks run:

1. nginx matches the upload location, runs `auth_request /bigbluebutton/media/checkUpload` before
   reading the body, and forwards `X-Media-Token`, `X-Original-Content-Length` and
   `X-Original-Method`.
2. `checkMediaBeforeUploading` refuses when the token is unknown or expired, when
   `Content-Length` is 0, or when it exceeds `maxMediaFileUpload`. On refusal it answers 403 with the
   header `x-file-too-large: 1` and sends the presenter a too-large message, exactly as
   `checkPresentationBeforeUploading` does.
3. `upload` consumes the token once
   (`MeetingService.consumePresentationUploadToken` is the model), checks that the token scope
   matches the `conference` parameter, checks the meeting is still running, and checks the mime type.
4. The file lands in `${mediaDir}/${meetingId}/${meetingId}/${mediaFileId}/` through a
   `Util.createMediaDir` sibling of `Util.createPresentationDir`
   (`bbb-common-web/src/main/java/org/bigbluebutton/api/Util.java:76`), under a name generated from
   `mediaFileId` and the extension, so a client-supplied name never reaches the filesystem.
5. bbb-web sends `MediaFileUploadedSysPubMsg`; akka marks the row complete and notifies the room.

Serving sequence:

1. The client builds the URL from `window.location.origin` plus the `public.mediaFile.sharingUrl` client
   setting plus `/meetingId/mediaFileId/filename` and appends `?sessionToken=<session token>`.
2. nginx matches the media location, runs `auth_request /bigbluebutton/media/checkAuthorization`, and
   serves the file with `X-Accel-Redirect` or `alias` so nginx itself answers `Range` requests.
3. `checkMediaAuthorization` reads `X-Original-URI`, extracts `sessionToken`, resolves the user
   session, and compares the meeting id in the path with `userSession.meetingID`, following
   `checkPresentationAuthorization` (`PresentationController.groovy:60`).

File extension rule: the filename is the last path segment and it keeps its extension, because the
player picks its backend from the extension. `react-player` accepts a URL only when
`canPlay.file` matches a known extension before the query string
(`react-player/lib/patterns.js`, `AUDIO_EXTENSIONS` and `VIDEO_EXTENSIONS` at lines 57 and 58, used
by `canPlayFile` at line 62). A URL that ends in an opaque id gets no player.

Byte-range rule: video seeking depends on `206 Partial Content`. Serving through the Grails stack does
not guarantee that, so the media location points at the file tree and lets nginx serve ranges, with
`auth_request` in front. This is the one place where the serving design differs from the
presentation download, which proxies to bbb-web.

| Key (proposed) | File | Default | Meaning |

| `public.mediaFile.sharingUrl` | `bigbluebutton-html5/private/config/settings.yml` | `/bigbluebutton/media` | Path the client appends to its own origin |
| `public.mediaFile` | same file | `{ enabled, sharingUrl, uploadEndpoint, mirroredFromBBBCore: { uploadSizeMax }, uploadValidMimeTypes }` | Top level block next to `externalVideoPlayer`. `public.media` already holds the WebRTC and audio bridge settings, so the feature does not belong there |

The mime whitelist lives in three places and all three change together, the way the presentation list
documents it at `settings.yml:1148`: the Java list in
`bbb-common-web/src/main/java/org/bigbluebutton/presentation/MimeTypeUtils.java`, the client list in
`settings.yml`, and the API document `docs/docs/development/api.md`. Phase 2 whitelist:
`mp3` (`audio/mpeg`), `m4a` (`audio/mp4`), `aac` (`audio/aac`), `ogg` (`audio/ogg`),
`wav` (`audio/wav`), `webm` (`video/webm`), `mp4` (`video/mp4`). `m4v` and `mov` are left out on
purpose: browsers refuse `video/x-m4v` and `video/quicktime` even when the codecs inside are
supported, so accepting them would promise playback the room cannot deliver.

Feature flag semantics match `externalVideos`: when disabled, the media area shows no entry and
`StartMediaFilePubMsgHdlr` ejects the sender with a reason, which is what
`StartExternalVideoPubMsgHdlr.scala` does for `disabledFeatures.contains("externalVideos")`.

## Recording contract (phase 3)

The recording path never uses the served URL. The URL carries a session token that expires with the
meeting, so a published recording cannot fetch it.

| Item | Contract |
|---|---|
| Record events | `StartMediaPlayerRecordEvent` (`mediaFileId`), `UpdateMediaPlayerRecordEvent` (`status`, `rate`, `time`, `state`) and `StopMediaPlayerRecordEvent`, module `MEDIA-FILE`, in `akka-bbb-apps/.../record/events/MediaPlayerRecordEvent.scala` and written by `RedisRecorderActor` |
| Segments | `BigBlueButton::Events.get_start_and_stop_media_file_events` in `core/lib/recordandplayback/generators/events.rb` turns the events into `{ start_timestamp, stop_timestamp, media_file_id, updates }`. A file the meeting ended on has no Stop event and runs to the last event |
| Archive | `raw_media_src: /var/bigbluebutton/media` in `core/scripts/bigbluebutton.yml`, copied to `<raw>/<meetingId>/media/<mediaFileId>/` by `core/scripts/archive/archive.rb`, and the source deleted after the last segment is archived, the way `delete_audio` handles raw audio |
| Published data | `media_files.json` at the root of the published package, written by `process_media_file_events` in `presentation/scripts/publish/presentation.rb`: one entry per played file, `{ timestamp, stopTimestamp, mediaFileId, filename, path, duration, updates }`, timestamps in seconds relative to the recording start, `duration` from ffprobe instead of the browser |
| Published bytes | the file copied to `<published>/presentation/<meetingId>/media/<mediaFileId>.<ext>`; `path` in the entry is relative to the recording root |
| Playback | implemented in the `bbb-playback` fork (`uplearn-media-file`, see `upstream-patches.md`): the recording clock stays the master, and the media element follows it. The entry active at the current time is the last one whose `timestamp` is reached and whose `stopTimestamp` is not; its position comes from the last update, advanced by (`time` - `timestamp`) * `rate` while that update says `play`. The element plays or pauses accordingly, and its `currentTime` is pulled back when it drifts more than 0.5 s, which is what reproduces a pause or a jump inside the file |
| Retention | a recorded meeting keeps its files until archiving finishes and then loses them with the source directory; a meeting without recording loses `mediaDir/<internalMeetingId>` at meeting end in `MeetingService.processMediaFileCleanup` |

`bbb-playback` is a separate repository, pinned at tag `v5.4.7` by `bbb-playback.placeholder.sh:3`, and
packaged by `build/packages-template/bbb-playback`. Phase 3 therefore spans two repositories and the
deb packages that carry them: `bbb-apps-akka`, `bbb-common`, `bbb-web`, `bbb-html5`,
`bbb-graphql-actions`, `bbb-graphql-server`, `bbb-record-core`, `bbb-playback-presentation`,
`bbb-playback`. Everything except the playback app is in this repository.

## Compatibility rules

Treat these as the API surface other teams build against. A change to any of them is a breaking change
and needs a note in `CHANGELOG` plus a version bump.

- The four action names and their input shapes.
- The `mediaFile` and `mediaPlayer` table columns, and the three view names.
- The route patterns, including the position of `meetingId`, `mediaFileId` and the filename in the serving
  path, because `checkMediaAuthorization` parses that path.
- The `public.mediaFile` client settings keys.
- The `media_files.json` file name and field names.

Not part of the surface: the Redis message names, which are internal to the apps, and the
`mediaUploadToken` format which the client treats as opaque.
